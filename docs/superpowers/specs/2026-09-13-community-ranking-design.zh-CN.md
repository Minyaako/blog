# 社区排行榜首版设计：站内投稿与审核

日期：2026-09-13

状态：设计方向已确认；按精简实现推进。首发登录提供方在认证接入前选定。

目标项目：`D:\seRver\apps\blog`。

决策依据：用户已选择“网页表单提交到服务器”，授权调整并压缩此前方案。本稿替代此前讨论中的 Git/PR 投稿、Sveltia 桥接、文件版本图和独立 studio 方案；沿用拖拽排序、派生、审核后公开和保留历史的产品目标。

## 1. 产品目标与首版取舍

用户在网站里完成“编辑 → 提交审核 → 查看结果”。普通投稿者不接触仓库、分支、PR、文件路径或版本 ID。任何访客可以阅读和试排，登录后可以投稿；管理员在站内审核。

| 保留 | 简化或延后 |
| --- | --- |
| 新建榜单、调整顺序、增删条目、编辑说明 | 首版仅纯文本，不做图片、富文本或条目资料库 |
| 从某个公开版本派生自己的榜单 | 保留来源链接，不做派生关系图或自动同步来源更新 |
| 本地自动保存、我的投稿、站内审核 | 草稿只在当前浏览器保存，不做云端草稿和实时协作 |
| 公开版本不可覆盖、查看历史 | 首版只提供相邻版本差异，不做任意两版比较或一键回滚 |
| 管理员分类与下架 | 分类用小型配置维护；下架以整份榜单为单位 |
| 与投稿解耦的站内身份 | 首版接入一种实际选定的登录方式，不限定 GitHub；多账号绑定界面延后 |

投稿要求有可验证、可再次登录的站内身份，不要求拥有 GitHub 账号。具体首发方式在认证接入前根据现有可用服务和目标用户选定；站内使用“登录后提交”等普通文案，登录页仅展示已实际接通的方式。不为了兼容多种可能性一次性部署多个认证服务。

本稿取消“创建 CMS 条目时生成 versionId”的约定：提交时生成投稿编号，审核通过时才生成公开版本编号。所有编号由服务器维护。

## 2. 最小架构

采用现有 Astro 应用 + Node 运行时 + 一个 SQLite 数据库。页面、同源 API 和管理界面放在同一个应用内，不另建通用 CMS、独立前端项目、队列或 Redis。

```text
访客浏览 / 编辑榜单
        ↓ 同域请求
现有 Caddy → Astro 应用
                ├─ 预生成的文章、归档、静态资源
                ├─ 排行榜页面、投稿 API、管理页
                └─ SQLite：身份、会话、投稿、公开版本
```

保留 Astro 默认静态预生成，只对排行榜、认证、投稿和管理相关路由启用按需渲染。公开榜单直接由服务器输出正文 HTML，关闭 JavaScript 仍可阅读；编辑和拖拽需要 JavaScript。Astro 支持通过适配器和路由级 `prerender = false` 混合这两种页面。[Astro 按需渲染文档](https://docs.astro.build/en/guides/on-demand-rendering/)

部署使用 `@astrojs/node` 的 standalone 模式，同一个进程提供预生成文件、动态页面与 API。具体适配器及数据库驱动版本在实施时按现有 Astro/Node 版本验证后固定。[Node 适配器文档](https://docs.astro.build/en/guides/integrations-guide/node/)

这意味着博客容器从纯 Caddy 静态容器变为 Node 应用容器，是本方案最大的部署变化。文章仍在构建时生成，读取文章不访问排行榜数据库；但 Node 进程整体故障仍可能影响整个博客。首版接受这一运行时耦合，换取一套应用和发布流程。数据库访问故障必须限制在排行榜路由内，不能由全站中间件传播到文章页。

SQLite 放在本机持久磁盘，仅运行一个应用实例，事务保持短小。当前按个人站点、少量投稿与单管理员审核设计，不建立多实例写入或网络共享数据库文件方案。SQLite 的单写者约束符合此假设；若实际出现持续写入争用，再迁移数据库。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

公开内容的唯一权威是数据库中已发布版本，不再从 Git 文件生成榜单。审核通过的事务提交后，下一次页面请求即可看到新版，不等待博客构建或部署。

## 3. 页面与编辑体验

| 页面 | 内容与操作 |
| --- | --- |
| `/ranking/` | 已发布榜单，按最近发布时间排序；分类筛选、分页、新建入口 |
| `/ranking/<rankingId>/` | 当前榜单、作者、来源、创建自己的版本、历史入口 |
| `/ranking/<rankingId>/?version=<versionId>` | 指定公开版本，明确标注“历史版本”及返回当前版本链接 |
| `/ranking/new/` | 空白榜单编辑；与详情内编辑复用同一套表单 |
| `/ranking/mine/` | 我的榜单和投稿状态，支持分页、查看原因、继续修改 |
| `/ranking/submissions/<submissionId>/` | 作者和管理员可见的投稿内容、状态和审核结果 |
| `/ranking/manage/` | 管理员待审队列、投稿预览与差异、通过/退回、已发布榜单下架/恢复 |

首版直接以服务器生成的 UUID 作为稳定 `rankingId` 和 URL 键，不让用户填写 slug。改标题不改地址；不建立标题冲突和 slug 迁移机制。历史列表放在详情页折叠区域，分页每页 20 条，不另建历史页面。

### 编辑表单

一套表单包含标题、简介、分类、排序列表及选填的“这次改了什么”。条目仅有名称和选填说明；顺序本身就是名次。元信息可折叠展示，但不再跳转 studio 填写。

在公开详情首次实际拖动、键盘抓取或点击“创建我的榜单”时，复制当前展示的确切版本，进入本地编辑态。查看历史版本时，复制的也是该历史版本。当前 URL 保持不变，顶部状态条明确表示正在编辑个人草稿。

默认操作总是派生新榜单。作者登录后另有“更新我的榜单”入口，只能从自己的当前公开版本开始更新；历史版本不直接更新原榜。匿名试排后登录不会自动把派生改成更新。

桌面允许拖动非交互区域；触屏仅从至少 44px 的手柄启动，正文保持自然滚动。按钮、链接、输入框不能触发拖动。提供可见的上移/下移按钮作为无需拖动的替代操作。

键盘支持 Enter/Space 抓取与放下、方向键移动、Home/End 到首尾、Escape 取消当前排序动作。焦点跟随条目，以一个 live region 报告位置变化。指针取消、失焦、页面隐藏等中断只撤销本次未完成拖动，保留此前编辑；空闲时 Escape 不退出编辑。

沿用已确认 V4 原型的手感作为基线：启动约 150ms、抬升约 1.035、位置跟随使用 rAF、邻项移动约 210ms、落位约 190ms、边缘自动滚动。位移阈值以 6px 起步。实现可在这些参数附近校准；减少动态效果模式关闭抬升、位移动画和落位动画。快速松手及中断后不能残留浮层、占位或事件监听。

“返回原榜”恢复进入编辑时的公开快照并保留草稿；再次进入时提供“继续草稿/重新开始”。“丢弃草稿”需要明确确认。提交前有一次同页内容预览，提示“通过审核后将公开”。

### 草稿与失败恢复

使用一个小型 IndexedDB 存储，不建设通用草稿框架。每个当前身份保留一份活动草稿；新建另一份前明确提示处理现有草稿。匿名草稿在登录后经用户确认归入当前账号，退出或换账号不得自动显示另一账号的草稿。

只保存 `draftId`、归属、意图、新建/更新目标、确切来源引用、工作内容、修订号、更新时间，以及提交重试所需的请求键和已发送内容快照。拖拽放下、增删后立即保存，文本输入短暂防抖；登录跳转和离页前主动 flush。保存成功才显示“已保存到此浏览器”。

每次保存使用 IndexedDB 同一读写事务比较修订号后写入。另一标签页已经更新时停止自动覆盖，提示重新载入；不做多标签实时合并，也不依赖 BroadcastChannel 保证一致性。

本地存储不可用时可以继续编辑和提交，但持续提示“当前草稿无法自动保存”，提供 JSON 导出及按同一 schema 校验的本地恢复。此时登录跳转前提示先下载草稿，不承诺刷新后自动恢复。断网、超时、登录过期、校验失败都保留当前页输入。公开阅读不依赖草稿存储。

草稿不承诺跨设备；已提交内容保存在服务器，可在其他设备登录后查看并重新载入编辑器。服务器未确认成功之前不清空草稿。成功响应仅将此次提交对应的草稿修订标记为已提交，不清除期间继续输入的新内容。

## 4. 投稿与审核：一个简单状态机

```text
本地草稿 ──提交──> 待审核 ──通过──> 已发布
                          ├─退回──> 已退回
                          └─撤回──> 已撤回

已退回 / 已撤回 ──载入修改并再次提交──> 一条新的待审核投稿
```

提交后内容固定，投稿状态可以改变。修改待审内容先撤回，再载入编辑；不允许管理员审阅期间后台悄悄替换正文。退回原因必填，撤回不必填原因。终态投稿仍可在“我的投稿”查看，只有公开版本进入公共历史。

每份榜单最多一条待审核投稿。退回或撤回后再投沿用原榜单 ID，但创建新的投稿 ID；不会产生多份空榜单。作者可以创建多份不同榜单。首版限每个账号最多 5 条待审投稿，并设可配置的提交频率与每日数量限制，避免一键连投占满队列。

审核页展示这次投稿的完整预览、来源或更新基线、条目增删/改名/改说明/位置变化，以及元信息变化。差异根据稳定 itemId 计算；移位只表示前后名次改变，不声称识别作者具体拖了哪一行。首版不实现逐字 diff。

管理员只有“通过”“退回”和已发布内容的“下架/恢复”，不在审核页代作者改文。管理员可以审核自己的投稿；不引入多人审批。所有审核与上下架记录操作者、服务器时间和原因。

审批在同一数据库事务内完成：

1. 确认投稿仍待审、目标未下架、分类可用、数据合法；首次发布派生榜单还须确认确切来源版本仍公开可见。
2. 更新投稿时，确认 `baseVersionId` 仍等于当前公开版本；新建时确认尚无公开版本。
3. 插入一个不可变的公开版本，序号在该榜单内递增，并记录上一个公开版本 ID。
4. 更新榜单当前版本指针，将投稿标记为已发布并关联新版本，写入审核记录。

上述任何一步失败都回滚。重复点击通过只返回已有结果；撤回和通过同时发生时，只允许一个状态转换成功。过期基线返回冲突并保留投稿，作者撤回后从当前版重新编辑，不自动覆盖或合并。

普通修改和派生分别检查所有权与来源：只有作者能更新原榜单；任何登录者能从可见的公开版本创建自己的榜单。来源后来发布新版不使派生失效；来源在首次审批前下架则不能发布这条派生投稿。已经公开的派生榜单独立审核后续更新，不因来源下架自动锁定。

## 5. 数据模型与不变量

首版保留少量关系表，完整内容存为结构化 JSON；不为每个条目和每个历史字段建独立表，不使用事件溯源。

| 表/配置 | 必要字段与职责 |
| --- | --- |
| `users` | 服务器生成且稳定的内部 `id`、展示名、创建时间；榜单、投稿与权限只引用内部 ID |
| `auth_identities` | userId、provider、subject；`(provider, subject)` 唯一，记录经服务器验证的登录身份 |
| `sessions` | 随机会话 token 的哈希、用户 ID、到期时间；退出时删除 |
| `rankings` | `id`、不可变 ownerId、可空的确切来源 rankingId/versionId、可空 currentVersionId、可见状态 |
| `submissions` | `id`、rankingId、authorId、baseVersionId、不可变 payload、请求幂等键与摘要、状态、提交/处理时间、退回原因、publishedVersionId |
| `versions` | `id`、rankingId、序号、parentVersionId、唯一 submissionId、不可变 payload、publishedAt |
| `moderation_events` | 目标、操作、操作者、时间、原因；与状态转换一起提交 |
| 分类配置 | 固定 ID、显示名称、排序、是否允许新投稿；由管理员维护应用配置 |

基础数据契约：

```ts
type RankingPayload = {
  schemaVersion: 1
  title: string
  description: string
  categoryId: string
  items: Array<{ itemId: string; name: string; note?: string }>
  changeNote?: string
}
```

作者、审核人、时间、可见状态和版本编号不是可填写的内容字段，由服务器从身份和事务推导。客户端新增条目用 UUID 标识；服务器验证格式和榜内唯一性。派生、改名、重排保留已有 itemId，新条目生成新 ID；itemId 不作权限凭据。

榜单 owner 和派生来源创建后不变，标题、简介、分类及条目通过新版本修改。公开作者展示由站内用户资料解析，登录提供方或其用户名不进入榜单内容契约，展示名变化不改变所有权。派生来源引用可指向较旧的公开版本，必须同时匹配其所属榜单。

数据库开启外键；明确保证版本属于目标榜单、父版本属于同一榜单、序号唯一、投稿只发布一次、每榜仅一条待审投稿。跨表约束由事务内检查及必要的约束/触发器共同保证。应用没有修改或删除公开版本正文的入口；数据库触发器防止普通路径误更新正文。`currentVersionId` 是允许更新的指针，取代此前“从文件图推导唯一 head”的复杂约定。

首版上限：标题 80 字、简介 1000 字、1–100 个条目、条目名称 120 字、说明 500 字、修改说明 500 字；文本长度按 Unicode 码点统一计算。HTTP 请求体另限 256 KiB。全部按纯文本转义输出，不解析用户 HTML/Markdown；数据校验在服务器执行，客户端仅用于及时反馈。

分类 ID 不删除或复用，停用后保留历史显示名称。停用分类的旧榜仍可阅读，但新投稿和审批要求选择可用分类。分类维护需要部署配置，首版不做分类 CRUD 管理页。

## 6. API、身份与请求边界

### 身份独立于登录提供方

用户最终澄清需要复用的是 **Waline**，不是 Sveltia。首版复用现有评论服务 `https://comments.minyako.top` 的登录，文章编辑器仍使用自己的登录。不新建账号密码系统，不额外接入社交平台，也不把评论管理员自动提升为榜单审核员。

排行榜后端携带 Bearer token 与本站 Origin 查询固定 Waline `/api/token`，只接受成功响应内的稳定 objectId。身份映射使用 `waline:<实例URL>` 与 objectId，不能按昵称、邮箱或客户端自报 ID/角色授权。请求限制超时、响应大小并禁止重定向；失效/封禁拒绝访问，网络故障返回暂不可用，公开榜单不受影响。[Waline API](https://waline.js.org/api/)

`provider` 是服务器配置的可信身份源命名空间，必须区分不同服务实例；OIDC 身份源绑定确切 issuer，`subject` 取经过验证的稳定 sub；其他提供方使用其稳定用户 ID。不能以显示名、可变用户名、用户输入的邮箱或客户端自报 ID 确认身份，也不能把同名 provider 重新指向另一个身份源而复用既有映射。OIDC 的稳定身份以 issuer 与 sub 联合确定。[OIDC 身份标识规则](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)

首次登录在事务内创建用户和身份映射，再次登录命中相同映射；唯一约束防止并发首次登录创建两个账号。首版不开放自行绑定、解绑和合并账号，不按相同邮箱自动合并身份。未来接入第二种方式时可以增加登录适配，但不承诺自动获得原账号内容；需要账号迁移时必须验证旧、新身份并保留内部 userId。管理员只按受限部署配置中的内部 userId 授权，不按某个提供方名称或公开资料字段授予权限。

### 会话与首发接入要求

复用 Waline 现有 `WALINE_USER` 登录状态及其登录页面，这是对早期“浏览器完全不持有提供方 token”约束的明确修订。榜单只添加薄适配：登录窗口同时校验消息 origin/source，接收凭据后交服务端验证，再轮换站内会话。不把 token 放入榜单 URL、日志或数据库。凭据由现有 Waline 浏览器存储保存，站内会话及校验所需的上游凭据另用 HttpOnly 主机 Cookie；记住登录最长 7 天，否则本站 Cookie 为浏览器会话期。

每次私有读取、写入都重新向 Waline 验证，且必须与本站会话对应同一内部账号。评论账号变化后暂停旧草稿；私有页面核对服务端渲染身份，不在新账号下继续展示或初始化旧账号投稿。浏览器退出串行等待在途身份交换，再撤销本站会话并清理本浏览器 Waline 状态。Waline 当前 token 删除接口不撤销所有设备的 JWT，因此不宣称全设备注销；不“记住登录”的凭据只在本标签页存储，并同步评论挂载状态。

会话 cookie 使用 Secure、HttpOnly、SameSite=Lax，不设置宽泛 Domain；服务端有明确到期时间。写接口验证登录、Origin 和会话绑定的 CSRF token，认证回调另按所用协议校验。后台每个端点都检查管理员身份；管理员先正常登录，再由可信维护流程把对应内部 userId 加入受限配置，不开放“首个注册者成为管理员”。

上线前验证现有 Waline 实例允许本站 Origin，真实账号能完成弹窗登录、评论凭据复用、投稿及退出。Facebook/QQ 等平台是否可用取决于该实例背后的认证服务；本次不新增第三方平台配置，也不要求用户粘贴 token。

| 接口组 | 首版职责 |
| --- | --- |
| `/api/ranking/auth/*` | 登录、回调、当前身份、退出 |
| `POST /api/ranking/submissions` | 提交新榜/派生/更新；创建或复用自己尚未发布的目标榜单 |
| `GET /api/ranking/submissions` 与 `GET .../<id>` | 当前用户的列表/详情；管理员可查看审核范围 |
| `POST .../<id>/withdraw` | 作者撤回待审稿 |
| `/api/ranking/manage/*` | 管理员队列、审批、退回、上下架 |

公开页面由服务器直接查询领域模块，无需为了 SSR 再请求自己的 HTTP API。首版不额外提供公共开发者 API。认证以外的领域逻辑集中于 schema、repository 和 service 三个小模块，不建立通用工作流引擎。

提交携带持久化到草稿中的 `requestId`。服务器按用户与 requestId 建唯一约束：同键同内容重试返回已有投稿；同键不同内容返回 409。摘要覆盖意图、目标、来源/基线和全部规范化内容。幂等记录与投稿在同一事务写入，重试查询先于“已有待审稿”限制。

发送时单独保存 `{requestId, draftRevision, 完整请求内容}`，后续编辑不能改写这份重试快照。结果未知时可继续本地编辑，但必须先用原请求键和原内容确认结果，才能再次投稿；成功后把服务器返回的 rankingId/submissionId 绑定到草稿，再处理撤回和重投。确认失败或完成上一请求后，新内容使用新键。请求超时不能直接当作提交失败另投一份。

未登录返回 401；无权访问其他人的私有投稿返回 404；状态或基线冲突返回 409；字段错误返回 422；体积超限返回 413；限流返回 429 与 Retry-After；服务不可用返回 503。前端展示可理解的原因并保留草稿。

提交频率默认每账号每分钟 3 次、每日 20 次新投稿，成功幂等重试不重复计数。另按可信代理提供的客户端 IP 限制请求速率，具体代理链在部署时核实；不直接信任任意客户端传入的转发头。首版不接验证码或外部反垃圾平台。

## 7. 公开阅读、历史与下架

列表仅包含有公开版本且可见的榜单，使用当前公开版本的分类、标题和发布时间。未审核内容永不进入公共页面、sitemap、搜索或社交预览。未发布榜单及不存在的版本返回 404，不能通过猜 ID 读取投稿。

正常详情 canonical 为稳定榜单地址；历史页 canonical 包含确切 version 参数并设 noindex；其他分页/筛选参数不进入 canonical。编辑、我的投稿、投稿详情和管理页均 noindex，敏感响应使用 `Cache-Control: private, no-store`，页面鉴权必须先于输出正文。

首版动态排行榜页面和相关 API 都不使用 CDN/共享缓存，并发送 no-store，避免审批或下架后仍返回旧正文。需要核对现有网关/CDN是否强制缓存这些路径；不能只依赖应用响应头。历史正文虽然不可变，可见状态仍可变化，因此也不使用永久缓存。

排行榜不进入构建期 Pagefind，页面仍保留分类筛选；全站搜索继续搜索静态博客内容。新增动态 `/ranking/sitemap.xml` 仅列当前可见榜单主地址；现有静态 sitemap 去掉示例榜单明细，通过 robots.txt 声明两个 sitemap。发布与下架不触发静态构建。

管理员下架整份榜单后，从列表与 sitemap 移除；其当前和历史公共地址返回 410，只显示通用下架提示，不输出标题、条目、作者及敏感原因。管理端保留完整数据和内部原因；恢复操作留审计记录。已下架榜单不允许继续提交更新或被新派生，已有待审稿不能通过。

此前要求的逐版本 tombstone 和公开作者/原因占位首版取消，以减少管理分支并避免在下架页继续暴露需要隐藏的内容。其他榜单的来源栏遇到隐藏来源时只显示“来源榜单已下架”，不再展开其标题、作者或正文。已发布的派生榜单是独立内容，不自动连带下架；管理端可按来源查找直接派生榜单，人工检查是否也需处理。服务不承诺撤回他人已复制的内容；确需物理删除时走单独维护流程，同时处理备份保留。

## 8. 部署、备份与现有代码衔接

已检查的本地基线：`astro.config.mjs` 为静态模式，`Dockerfile` 最终镜像为 Caddy；`deploy/compose.yml` 根文件系统只读，`/data` 是临时文件系统；`deploy/bin/blog-release` 会先启动候选容器。当前 `ranking-fixtures.ts` 只有两个明确标注虚构的演示榜单。以上为工作区证据，不代表已检查生产实时配置。

实施必须同步完成以下集成，不能仅添加表单：

- 添加 Node 适配器、按需路由与服务器代码；构建期不连接生产数据库、不需要生产认证凭据。
- Docker 运行镜像改为固定版本的 Node，保留非 root、只读根文件系统和现有 `server_proxy`/8080 边界。数据库使用专用挂载，例如宿主 `/srv/apps/blog/ranking-data` → 容器 `/var/lib/blog-ranking`；不能写入现有 tmpfs `/data`。
- Node 只在容器内运行，宿主不新增 Node/pnpm 安装要求。新登录凭据只在运行时以受限 secret 文件注入；原有文章编辑器、评论服务及其数据库独立。
- Pagefind 构建输入和相关产物检查适配 Node 输出中的静态目录，不能沿用全部位于 `dist/` 根目录的假设。保留文章、RSS、归档、资源缓存头、404、尾斜杠及现有安全头行为。
- 排行榜读写数据库故障返回局部 503；进程存活检查与排行榜数据库就绪检查分开，前者不能把数据库临时故障变成全站重启循环，发布验收须验证后者。
- 候选容器使用独立临时测试数据库，绝不能自动迁移生产库。生产迁移作为发布中的显式受控步骤：停止写入、完成一致性备份、单次迁移，再启动正式进程；启动时只检查 schema 兼容性，不自动破坏性迁移。
- 扩展当前发布器与部署测试，明确数据库目录、运行时秘密、就绪检查和迁移阶段。首次部署需要服务器管理员按既有基础设施边界准备目录、凭据和代理规则；文档本身不代表已完成这些操作。

数据库是运行时数据，不能进入 Git、公开镜像、CI artifact、浏览器包或预览环境。PR/公开预览只使用独立虚构测试数据和隔离登录配置；生产会话、认证回调及验证通道不给预览域名复用。

备份采用 SQLite 一致性备份接口，不能直接复制写入中的数据库主文件。每日一份保留 14 天，每周一份保留 8 周；备份包含完整数据库及必要版本标识，校验完整性，并保存一份受限访问的异机副本。异机目的地、凭据和实际恢复演练是上线条件，不在本稿中假定已经具备。[SQLite 备份文档](https://www.sqlite.org/backup.html)

应用回滚不回滚投稿数据。首版迁移尽量只做可向后兼容的扩展；若旧镜像不能读取新 schema，则先进入只读维护状态，由管理员恢复兼容应用或执行经过验证的数据恢复。恢复旧备份会丢失备份后的投稿，不能用自动回滚暗中执行。恢复数据库后使已有登录会话失效，并重新核对下架记录，防止恢复操作重新公开已下架内容。

虚构 fixture 只留作测试材料，不导入生产为真实作者的投稿。旧的 `/ranking/visual-novels/`、`/ranking/restaurants/` 返回带“示例已结束”提示的 410 页面；新站初始为空列表，通过管理员真实投稿填充。删除旧 fixtures 对 sitemap/页面的生产依赖，并调整当前明确假定“无 ranking collection/只有 fixtures”的测试；仍不创建 Astro ranking 内容 collection。

本次不改 `apps/blog-editor*`，不复用或调整其 Sveltia 授权。既有博客正文管理继续保留。实现前需先处理本地与远端代码基线的差异，在保留现有用户文件的前提下选定实施起点；本稿没有执行拉取、合并、提交或推送。

## 9. 验收与交付边界

只围绕核心行为验证，不为每个字段或内部方法单独制造测试任务。

1. 完整路径：访客试排 → 登录 → 草稿恢复 → 提交 → 管理员退回 → 修改重投 → 审批 → 公共页面立即读到内容；全程不出现仓库授权和 PR 操作。
2. 版本：派生引用确切旧版本且不修改来源；作者更新保留原 ID；拒绝他人更新、伪造来源、过期基线和重复发布；重命名/移位仍保持 itemId。
3. 并发与恢复：双击/超时重试只产生一条投稿；通过与撤回竞态仅一方成功；审批失败无半发布状态；多标签保存冲突不覆盖；登录过期和存储失败不清空输入。
4. 访问控制与身份：重复登录映射到同一内部 userId；不同身份源的相同 subject 不混淆，不按同名/同邮箱合并；匿名与其他用户无法读取私有投稿；普通用户不能访问管理操作；CSRF/跨站请求被拒绝；非法输入按纯文本显示且请求体与频率限制有效。实际首发登录方式另验证其登录、退出、过期及恢复流程。
5. 阅读与交互：无 JavaScript 可读公开和历史内容；桌面、触屏、键盘、减少动态效果、快速松手和拖拽中断均符合第 3 节；深浅主题及小屏表单不遮挡操作。
6. 可见性：未审稿及下架正文不能出现在公共 HTML、接口、社交元信息、sitemap 和 Pagefind；下架后新请求不可读旧正文；隐藏来源不能继续用于新投稿。
7. 部署：真实 Node 镜像启动、静态博客回归、运行时数据库重启后仍在、候选容器不接触生产库、迁移失败安全退出、兼容回滚及隔离恢复演练。

实现按三个可验收阶段组织：先完成数据/登录/提交/审批的纵向闭环，再接入编辑器和公开历史，最后完成部署、备份与端到端验收。各阶段由未参与实现的独立 agent 审查，不再逐字段或逐小节请求用户确认。

- 当前目标：为博客社区排行榜形成可直接指导实施的精简设计。
