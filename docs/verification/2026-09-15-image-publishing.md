# OCI 镜像发布验证

## 故障证据

主题变更的验证和媒体发布均通过。运行 `34864592179` 在镜像本地导出完成后停于 `pushing layers` 超过 20 分钟，取消后未产生远端 SHA 清单。运行 `34869428852` 增加 12 分钟超时后仍停在相同阶段。运行 `34872663166` 将 BuildKit v0.32.2 的仓库并发限制为 1 后再次在上传阶段超时。上述日志没有证明具体是哪一方的网络故障，生产始终保留上一健康版本。

## 替代上传路径

BuildKit 只构建一次 OCI 归档，明确保留 `mode=max` provenance；Skopeo 使用现有 Docker 认证文件执行全量、保摘要复制。脚本只接受本仓库的完整提交 SHA 标签，要求归档带有与平台镜像关联的构建证明，且目标不存在或内容完全相同。认证失败、网络异常、摘要不一致均终止发布，不进入部署步骤。重跑仍只检查已存在的 SHA 镜像，不重新构建或复制。

## 本地实测

- 临时 BuildKit v0.32.2 从不含业务数据的 `FROM scratch` 测试目录生成带 `mode=max` provenance 的 OCI 归档。
- Ubuntu 官方包 Skopeo 1.13.3 执行 `oci-archive → oci`，使用 `--all --preserve-digests`，成功复制平台镜像及 attestation 两份 manifest。
- 归档内实际镜像 index 与复制后 index 均为 `sha256:99b36ea9270e2c7d5458b0ca081b79c76a5c9018f2588cee1d7f8072fa6493a9`。没有压缩或媒体类型转换。
- 部署配置测试验证首次发布条件、OCI exporter、构建 secret、上传步骤及原部署依赖。

本地实测证明该工具组合能保留完整产物；CCR 实际上传和生产发布仍需由后续 main 流水线验证，不能仅凭本地复制成功判定已经上线。
